## 4. 互联网模式 + 去中心化地址表同步（完整 gossip）——你第 7 点细化定稿

目标：**把对 Workers 的请求压到极低**，机器之间自组织同步；Workers 只作「保底目录」。

### 4.1 Workers 角色（保底目录，非实时）
- 端点在 `/machine_list/*`：`/bootstrap`(GET 保底表) 、`/announce`(POST) 、`/delete`(DELETE/POST) 、`/merge`(POST 一批 url)。
- **长 TTL**（约 30–60 分钟），**不主动删**，仅长时间掉线才删，保证表“丰富可 ping”。
- 机器「冷启动」或本地全 ping 不通时才去请求它。

### 4.2 每台机器维护一张「在线地址表」
- 条目含：`{nodeId, lan:{ip,port}, pub:{url}, name, lanNick/inetNick, lastSeen, md5?}`。
- **表 MD5**：对所有条目做规范化序列化后取 MD5，作为同步裁决指纹。
- 表来源合并：LAN 扫描/信标发现 + Workers bootstrap + 其它机器拉来的表。

### 4.3 冷启动 & 恢复（你的流程 1）
1. 读**本地持久化的上次地址表**（上次退出前保存）。
2. 逐个 ping 本地表里的**互联网穿透地址**（pub url `/health`）；能 ping 通一台 → 向它索要**最新地址表**并以其为准。
3. 一台都 ping 不通 → 向 Workers `GET /machine_list/bootstrap` 取保底表。
4. 仍无 → 空表，仅本机。

### 4.4 常态同步（你的流程 2/3）
- 周期（约每 5s）对表内机器做 **ping/健康 + 询问其表 MD5**。
- 若对方 MD5 ≠ 自己 MD5：
  - 比较**表最后修改时间**，取较新者；
  - 拉取较新表，按 `nodeId` 合并（新机器加入、消失机器标记下线）。

### 4.5 动态加入 & 下线（你的流程 4/5）
- 有人向我拉表且其 nodeId 不在我表内 → 加入。
- 连续 N 次（如 3 次 × 周期）ping 不通某 pub url → 从自己表删除；若 LAN 条目持续无信标 → 删除。
- 删除/大变化后可选回写 Workers `/merge`，但**压低频率**。

### 4.6 Workers 刷新（你的流程 6）
- 约每 10 分钟，从当前表挑 3–4 台机器 `POST /machine_list/merge` 把（去重、仍在线）的表上报，刷新保底目录丰富度。
- 目的：保证 Workers 表里**至少有一台可 ping**，供冷启动机器索表。

### 4.7 保底与更新策略（你的流程 7）
- 若当前表内**互联网 pub 地址过少/过旧**，就主动向 Workers 上报当前表并提示「地址过少需更新」。
- Workers 端只删「长时间掉线」的条目，保持丰富。

### 4.8 频控目标
- 单机对 Workers 的正常稳态：仅 10 分钟一次 merge + 冷启动 bootstrap ≈ 极低（远低于 Cloudflare 免费限额 ~100k/日）。
- 机器间表同步走 P2P，不打 Workers。
